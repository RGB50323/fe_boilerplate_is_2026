# H09: disponibilidad y revisión FE-9.1 / FE-9.2

## Backend requerido

Configurar `API_URL=http://localhost:3000/api/v1` en `.env.local` y ejecutar
el backend de H09 con los horarios del seed. No publicar `.env.local`.

- `GET /api/v1/sucursales`: sucursales y horarios reales.
- `GET /api/v1/sucursales/:id/mesas-disponibles`: disponibilidad.

Ambos endpoints son públicos; no requieren token. La ruta con guion coincide
con el diseño técnico H09. El servidor de Next realiza estas llamadas:
no aparecen como requests directos al backend en Network del navegador.

## Comportamiento

“Buscar mesas” está deshabilitado con filtros inválidos o durante la búsqueda.
La validación se conserva en cliente, Server Action y backend. Después de
buscar, los cambios válidos consultan automáticamente con 350 ms de debounce;
las respuestas antiguas no reemplazan resultados nuevos.

Un 400/404 con `errores` se presenta junto al campo. `id` del backend se
asocia al selector `sucursalId`. Los errores desconocidos o de conexión se
presentan en la alerta general con reintento. Los errores de horarios incluyen
“Horario no válido”.

## Integración pendiente de H10

H10 todavía no tiene página ni formulario implementados. La tarjeta muestra
“Reservar” deshabilitado y un aviso; no navega a una ruta inexistente ni
simula una reservación confirmada.

`DisponibilidadForm` acepta un callback opcional `onReservar` para la futura
integración desde un componente cliente. Cuando se conecte, recibirá los datos
del resultado seleccionado:

```ts
{ mesaId: number, sucursalId: number, fecha: string, hora: string, personas: number }
```

La ruta frontend de destino está pendiente de acuerdo. Quien implemente H10
conectará ese callback a la navegación y conservará los datos durante el login.
No pasar un Server Action como callback de navegación desde la página servidor.

El contrato acordado para confirmar es `POST /api/v1/reservaciones`, con
`mesaId`, `fecha`, `hora`, `personas`, `nombre`, `telefono` y `correo`.
H10 deberá obtener nombre/teléfono/correo en su formulario, exigir sesión y
tratar 400, 401, 404 y 409. `clienteId` nunca se envía desde el formulario:
el backend lo obtiene de la sesión autenticada.

Este PR deja preparada la entrega de datos, pero **no completa la navegación
de FE-9.2** hasta que exista H10. No implementa ni invoca el POST de H10.

## Pruebas

- `npm test`: validaciones, horarios, acciones HTTP simuladas e interacción del
  formulario (éxito, vacío, loading, errores, debounce, respuestas antiguas,
  botón deshabilitado y datos entregados a H10 mediante el callback).
- `npm run test:watch`: las mismas pruebas durante el desarrollo.
- `npm run lint` y `npm run build`.

Las pruebas de componentes simulan las Server Actions; las pruebas de acciones
simulan fetch. No sustituyen una prueba de navegador con ambos servidores.
